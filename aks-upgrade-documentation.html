AKS Upgrade Overview
Understand the upgrade strategy, scope, and version compatibility before you begin.
⚠️
Minor version skipping not supported

AKS only allows upgrading one minor version at a time (e.g. 1.27 → 1.28 → 1.29). You cannot skip minor versions. Patch upgrades within the same minor are allowed.

🔑

Control Plane First

Always upgrade the AKS control plane (API server, etcd, scheduler) before upgrading node pools. The control plane must be N+1 above node pools.

🔃

Node Pool Rolling

Node pools are upgraded via cordon → drain → replace (surge). AKS cordons old nodes, drains pods, creates new nodes with new version, deletes old nodes.

🔒

Zero Downtime Goal

With correct PodDisruptionBudgets and surge settings, most workloads survive with zero downtime. Critical apps need PDBs configured before upgrade.

📐

AKS Node Upgrade Internals
1. Cordon old node
Mark node as unschedulable — no new pods admitted
2. Create surge node
New node with upgraded K8s version is provisioned (maxSurge=1 by default)
3. Drain old node
Pods evicted respecting PodDisruptionBudgets, rescheduled on new node
4. Delete old node
Old VM deleted after successful drain. Process repeats for each node.
5. Validate node pool
All nodes Ready with new version. Node pool upgrade complete.

Estimated Upgrade Duration

Control plane: ~10-15 min | Per node: ~5-10 min | 10-node cluster: ~1-2 hrs total

Complete CLI Commands Reference
All Azure CLI and kubectl commands for upgrading AKS clusters.
🔍

Step 1 — Pre-Upgrade Recon

bash
# Set variables
export CLUSTER_NAME="aks-prod-cluster"
export RESOURCE_GROUP="rg-production"
export TARGET_VERSION="1.28.5"

# Login to Azure
az login
az account set --subscription "your-subscription-id"

# Get current cluster version
az aks show --resource-group $RESOURCE_GROUP --name $CLUSTER_NAME --query "kubernetesVersion"

# List available upgrades
az aks get-upgrades --resource-group $RESOURCE_GROUP --name $CLUSTER_NAME --output table

# Connect kubectl to the cluster
az aks get-credentials --resource-group $RESOURCE_GROUP --name $CLUSTER_NAME --overwrite-existing

# Verify node versions
kubectl get nodes -o wide

# Check all running pods
kubectl get pods -A --field-selector 'status.phase!=Running'
⚠️

Step 2 — API Deprecation Check

bash
# Install kubent (Kube No Trouble)
sh -c "$(curl -sSL https://git.io/install-kubent)"

# Run API deprecation scan against target version
kubent --target-version $TARGET_VERSION

# Export all manifests for review
kubectl get all -A -o yaml > all-manifests-backup.yaml

# Check specific deprecated API groups
kubectl api-resources --verbs=list --namespaced -o name | xargs -n 1 kubectl get --show-kind --ignore-not-found -A

# Check PodSecurityPolicies (removed in 1.25)
kubectl get psp 2>&1
⬆️

Step 3 — Upgrade Control Plane

🚨
Important

Upgrade control plane first. Do NOT use --node-image-upgrade-only flag here. This is a one-way operation — no in-place downgrade.

bash
# Upgrade control plane only (RECOMMENDED FIRST STEP)
az aks upgrade \
  --resource-group $RESOURCE_GROUP \
  --name $CLUSTER_NAME \
  --kubernetes-version $TARGET_VERSION \
  --control-plane-only \
  --yes

# Wait and verify control plane is updated
az aks show --resource-group $RESOURCE_GROUP --name $CLUSTER_NAME \
  --query "kubernetesVersion"

# Verify all system pods are running
kubectl get pods -n kube-system

# Check API server version
kubectl version
🔄

Step 4 — Upgrade Node Pools

bash
# List all node pools
az aks nodepool list --resource-group $RESOURCE_GROUP --cluster-name $CLUSTER_NAME --output table

# Upgrade system node pool FIRST
az aks nodepool upgrade \
  --resource-group $RESOURCE_GROUP \
  --cluster-name $CLUSTER_NAME \
  --name systempool \
  --kubernetes-version $TARGET_VERSION \
  --no-wait

# Watch nodes upgrade in real-time
kubectl get nodes -w

# Check node pool upgrade status
az aks nodepool show \
  --resource-group $RESOURCE_GROUP \
  --cluster-name $CLUSTER_NAME \
  --name systempool \
  --query "provisioningState"

# Upgrade user node pools (one at a time)
az aks nodepool upgrade \
  --resource-group $RESOURCE_GROUP \
  --cluster-name $CLUSTER_NAME \
  --name userpool1 \
  --kubernetes-version $TARGET_VERSION

# Set max surge for faster upgrade (increases cost temporarily)
az aks nodepool update \
  --resource-group $RESOURCE_GROUP \
  --cluster-name $CLUSTER_NAME \
  --name userpool1 \
  --max-surge 2
✅

Step 5 — Post-Upgrade Validation

bash
# Verify all nodes are on new version and Ready
kubectl get nodes -o wide

# Check for any not-running pods
kubectl get pods -A | grep -vE 'Running|Completed'

# Check kube-system health
kubectl get pods -n kube-system -o wide

# Verify CoreDNS
kubectl get deploy coredns -n kube-system
kubectl run dns-test --image=busybox:1.28 --restart=Never --rm -it -- nslookup kubernetes

# Check Ingress controller
kubectl get pods -n ingress-nginx
kubectl get svc -n ingress-nginx

# Run a quick deployment test
kubectl run test-pod --image=nginx:latest --restart=Never
kubectl wait --for=condition=ready pod/test-pod --timeout=60s
kubectl delete pod test-pod

# Check PVC / PV are still bound
kubectl get pvc -A | grep -v Bound

# Check HPA status
kubectl get hpa -A

# Final: confirm cluster version
az aks show --resource-group $RESOURCE_GROUP --name $CLUSTER_NAME \
  --query "{controlPlane:kubernetesVersion,agentPoolProfiles:agentPoolProfiles[].{name:name, version:orchestratorVersion}}"
Post-Upgrade Dependency Checks
Run these checks after every upgrade to catch broken dependencies before users notice.
🚨
Common post-upgrade failures to watch for

Admission webhooks, RBAC changes, removed APIs (PSP in 1.25, PodSecurityPolicy, deprecated metrics), Helm chart CRD mismatches, and add-ons using old API versions are the most common causes of post-upgrade issues.

🔗

Dependency Issue Checklist

ComponentWhat to CheckCommandCommon Issue
CoreDNS Pod status + DNS resolution kubectl get pods -n kube-system -l k8s-app=kube-dns ⚠️ ConfigMap overrides reset
Azure CNI / kubenet Pod-to-pod connectivity kubectl run nettest --rm -it --image=nicolaka/netshoot -- bash ⚠️ IP allocation errors after node churn
Ingress Controller Controller pod + IngressClass kubectl get ingressclass && kubectl get ingress -A ❌ networking.k8s.io/v1beta1 removed in 1.22
cert-manager Webhook + CertificateRequests kubectl get cert -A && kubectl get cr -A ❌ Webhook fails → ALL pod creates blocked
Prometheus / Grafana CRDs, ServiceMonitors kubectl get servicemonitor -A && kubectl get prometheusrule -A ⚠️ Deprecated metrics removed (e.g. scheduler_e2e_scheduling)
Velero / Backup BackupStorageLocation health kubectl get backupstoragelocation -n velero ✅ Usually auto-recovers, verify Available
KEDA ScaledObject + TriggerAuthentication kubectl get scaledobject -A && kubectl get ta -A ⚠️ CRD version mismatch between KEDA and K8s
Istio / Linkerd Sidecar injection + mTLS kubectl get mutatingwebhookconfigurations ❌ Webhook cert expiry → sidecar injection fails
Persistent Volumes PVC bound + StorageClass kubectl get pvc -A | grep -v Bound ⚠️ CSI driver pods may restart during node churn
Azure AD / AAD Pod Identity AzureIdentity binding kubectl get azureidentity -A && kubectl get azureidentitybinding -A ❌ Deprecated in favor of Workload Identity in 1.28+
Workload Identity ServiceAccount annotations kubectl get sa -A -o jsonpath='{.items[*].metadata.annotations}' ✅ Should work; verify token projection
HPA / VPA Metrics server + HPA targets kubectl get hpa -A && kubectl top nodes ⚠️ metrics.k8s.io v1beta1 changes in 1.26+
💥

Admission Webhook Failures

Broken admission webhooks are the #1 cause of post-upgrade cluster issues. They block ALL pod creation.

bash
# List all webhooks
kubectl get mutatingwebhookconfigurations
kubectl get validatingwebhookconfigurations

# Check webhook endpoint reachability
kubectl get svc -A | grep webhook

# Temporarily disable a broken webhook
kubectl delete mutatingwebhookconfiguration <name>
📦

Helm Chart Compatibility

Helm charts may embed API versions incompatible with the new Kubernetes version.

bash
# List all helm releases
helm list -A

# Check for outdated charts
helm list -A -o json | jq '.[].chart'

# Upgrade a helm chart post-cluster upgrade
helm upgrade cert-manager jetstack/cert-manager \
  --namespace cert-manager \
  --reuse-values

# Check helm release status
helm status cert-manager -n cert-manager

Rollback Plan
Kubernetes upgrades cannot be downgraded in-place. Rollback requires restore from backup.
🚨
AKS Upgrade Rollback Limitation

There is NO in-place downgrade for AKS. Once an upgrade is complete, you cannot roll back to the previous version directly. Rollback requires either: (a) restoring a snapshot, or (b) recreating the cluster from backup (Velero). This is why pre-upgrade backup is MANDATORY.

⚡

Rollback Trigger Criteria

  • !
    Critical pods CrashLoopBackOff > 10 minAfter node pool upgrade, if core services won't recover
  • !
    Ingress completely non-functionalAll HTTP/HTTPS traffic returning 500 or timing out
  • !
    Database connectivity lostApplications cannot connect to databases post-upgrade
  • !
    PVC mount failuresStateful applications fail to mount persistent volumes
  • ⚠
    Admission webhook blocking all createsNo new pods can be scheduled — evacuate traffic first
🔧

Immediate Mitigation Steps

T+0 — Declare incident
Page on-call team. Freeze all deployments. Notify stakeholders.
T+5min — Identify scope
kubectl get pods -A | grep -v Running — identify all failing services
T+15min — Try quick fixes
Restart pods, fix webhooks, apply corrected manifests if API version issue
T+30min — Decide: fix or restore
If quick fixes fail → initiate Velero restore or new cluster provision
T+60-120min — Service restored
Cluster restored from backup or new cluster live with traffic routed
🔄

Velero Restore Commands

bash
# List available backups
velero backup get

# Describe a specific backup
velero backup describe pre-upgrade-backup-20250518 --details

# Restore from backup (all namespaces)
velero restore create --from-backup pre-upgrade-backup-20250518

# Restore specific namespace only
velero restore create --from-backup pre-upgrade-backup-20250518 \
  --include-namespaces production,monitoring

# Watch restore progress
velero restore describe <restore-name> --details
velero restore logs <restore-name>

# Take a pre-upgrade backup (run BEFORE upgrade)
velero backup create pre-upgrade-backup-$(date +%Y%m%d) \
  --include-namespaces '*' \
  --wait
